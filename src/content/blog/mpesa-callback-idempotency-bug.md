Every M-Pesa Daraja integration we've inherited from another team has hit this bug once, in production, usually during a busy period — and it's almost never caught in sandbox testing, because the sandbox rarely reproduces the network conditions that trigger it.

## The failure mode

Safaricom's Daraja API sends an asynchronous callback to your registered URL once a C2B or STK Push transaction completes. If your endpoint doesn't respond quickly enough, or the response gets lost on a flaky connection, Daraja's platform — reasonably, from its side — treats the callback as undelivered and retries it. Your merchant system, meanwhile, already processed the first delivery. Without protection, it processes the retry too: the customer's ledger gets credited twice, or a paid order gets marked as paid a second time and re-triggers downstream fulfillment.

This isn't a Daraja bug. Retry-on-uncertain-delivery is correct, defensible behavior for any payment webhook — Stripe, PayPal, and every other processor we've integrated does the same thing. The bug is entirely on the receiving side: a webhook handler that assumes "I've never seen this request before" without checking.

## The fix is one field, applied consistently

Every M-Pesa callback carries a value that's unique per transaction — the `MpesaReceiptNumber` for C2B, or the `CheckoutRequestID` for STK Push. Treat that value as an idempotency key: before processing a callback, check whether you've already recorded a transaction with that exact key. If you have, acknowledge the webhook with a 200 (so Daraja stops retrying) and stop — don't re-run the settlement logic.

```
const tx = await ledger.match({
  checkoutRequestId: body.CheckoutRequestID,
  amount: body.Amount,
  idempotencyKey: body.MpesaReceiptNumber,
});

return tx.status === "matched"
  ? ledger.settle(tx.id)   // first delivery — process normally
  : ledger.flag(tx.id);    // already seen — acknowledge, don't reprocess
```

The subtlety is *where* this check lives. It needs to happen inside the same transaction as the settlement write, not as a separate pre-check — two concurrent retries arriving milliseconds apart (which does happen, under real network conditions) can both pass a "have I seen this before" check that isn't atomic with the write that follows it.

## Why sandbox testing doesn't catch it

Daraja's sandbox environment is remarkably reliable — which is exactly why it doesn't surface this bug. It rarely triggers the retry path, because it rarely has the delivery uncertainty that causes a retry in the first place. The first time most teams see this behavior is in production, under real mobile network conditions, usually weeks after launch. We build the idempotency check in from day one on every Daraja integration specifically because we can't rely on testing to surface it before a client does.
