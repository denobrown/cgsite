# CloudGrid Africa — cloudgridafrica.com (v3 rebuild)

Full static Astro rebuild. Every route compiles to plain HTML/CSS at build
time; the only runtime JavaScript on the site is three small, external,
single-purpose files under `public/scripts/` — never inline `<script>`
blocks.

**Primary deploy target: Vercel.** Netlify remains fully supported as a
fallback (`npm run build:netlify`) — see "Vercel vs. Netlify" below for
exactly what differs between the two.

## Deploying to Vercel (current primary target)

1. Push this repo to GitHub if it isn't already there — required for both
   normal deploys and for `api/generate-daily-post.js`'s auto-commit
   pipeline to trigger a rebuild.
2. Import the repo into Vercel (**Add New → Project**). Framework
   auto-detects as Astro; leave build settings at their defaults —
   `package.json`'s `build` script already runs
   `astro build && node scripts/generate-headers-vercel.mjs`.
3. Set environment variables in **Project Settings → Environment
   Variables** — see `.env.example` for the full list
   (`GITHUB_TOKEN`, `GITHUB_REPO`, `GITHUB_BRANCH`, `CRON_SECRET`,
   `RESEND_API_KEY`).
4. Deploy. Vercel Cron (configured in `vercel.json`) fires
   `api/generate-daily-post` once daily; Vercel Functions serve
   `api/feed` and `api/contact`.

**One workflow habit this introduces:** `vercel.json`'s `headers` array is
regenerated by every `npm run build` and needs to be committed like any
other build artifact that matters — see "Vercel vs. Netlify" below for why
Vercel doesn't support the same
dist/_headers-generated-and-picked-up-automatically pattern Netlify does.
If you add a new blog post locally and push without running `npm run
build` first, the deployed CSP simply won't include that post's structured-
data hash yet — Vercel will still build and deploy fine, the JSON-LD block
on that one page will be silently dropped by the browser's CSP enforcement
until the next commit that includes a regenerated `vercel.json`. Not
dangerous, just worth knowing: the fix is running a build before you push,
not something to debug in production.

## Vercel vs. Netlify — what's actually different

| Piece | Netlify | Vercel |
|---|---|---|
| Functions | `netlify/functions/*.js` | `api/*.js` (Edge runtime) |
| Feed proxy | `netlify/functions/feed.js` | `api/feed.js` — same allowlist logic, ported |
| Daily post generator | `netlify/functions/generate-daily-post.js`, Netlify Scheduled Functions | `api/generate-daily-post.js`, Vercel Cron (`vercel.json`), secured via `CRON_SECRET` |
| Contact form | Netlify Forms (`data-netlify="true"`) | No native equivalent — `api/contact.js` + Resend, still a plain HTML POST with zero client JS |
| Chat widget backend | `netlify/functions/chat.js` | `api/chat.js` — same grounded system prompt, same limits, both proxy to Claude server-side only |
| Security headers | `dist/_headers`, auto-picked-up from the publish directory | `vercel.json`'s `headers` array, static/committed config — see the workflow note above |
| Header generator script | `scripts/generate-headers-netlify.mjs` | `scripts/generate-headers-vercel.mjs` |

Both function-proxy paths are unified at `/api/feed`, `/api/contact`, and
`/api/chat` in the actual site markup/JS — on Netlify, `netlify.toml`
rewrites those paths to the `.netlify/functions/*` equivalents, so
`ContactSection.astro`, `tech-intel-hub.js`, and `chat-widget.js` never need
to know which platform they're running on.

## What changed vs. the previous single-file `index.html` site

- **Architecture:** single-file `index.html` → Astro project with real
  routing, a content collection for the blog, and component-level
  isolation. Still compiles to pure static output for Netlify.
- **Fonts:** Google Fonts CDN → self-hosted via `@fontsource-variable/*`.
  Removes a third-party network origin entirely; `font-src` in the CSP is
  just `'self'`.
- **CSP:** was hash-pinned per inline `<script>` edit via your existing
  `pin_csp.py`. In this rebuild, **only one inline script exists on the
  entire site** — the Organization JSON-LD block in `Layout.astro` — and
  its content is fixed (not built from per-page props), so its hash never
  changes on ordinary content edits. Every other script is an external file
  under `/scripts/`, covered by `script-src 'self'` with no hash needed at
  all. Run `pin_csp.py` against `dist/` once after any future edit to that
  one JSON-LD block; you should rarely need to touch it otherwise.
- **Tech Intel Hub feed proxy:** the old function accepted an arbitrary
  `?url=` parameter — an SSRF primitive. `netlify/functions/feed.js` now
  only accepts an exact `source` key from a fixed allowlist. See the
  comment block at the top of that file.
- **Blog:** the RSS widget had no per-post URLs and wasn't indexable. It's
  now a real Astro content collection (`src/content/blog/`) with static
  per-post pages, a working `/rss.xml`, and a documented daily-publish
  mechanism (below) — while the live RSS aggregation you liked survives as
  the Tech Intelligence Hub, restyled and hardened.

### Why the security tip is build-time, not client-JS

It doesn't need per-second freshness the way a clock does. Computing it in
`LiveSystemsStrip.astro` frontmatter (day-of-month index into
`security-tips.json`) means zero JS for that segment and a tip that's
correct as of the last deploy. Since `generate-daily-post.js` (below)
triggers a deploy once a day via its GitHub commit, the tip rotates daily in
practice without needing its own scheduled job.

### How daily auto-posting actually works

A static site has no runtime database and no write access to its own
deployed files. The correct pattern — and what `netlify/functions/
generate-daily-post.js` implements — is:

1. Netlify Scheduled Function fires once daily (`0 5 * * *`, 08:00 EAT).
2. It curates a short digest from a fixed set of source feeds (same
   allowlist pattern as the Tech Intel Hub proxy).
3. It commits a new Markdown file matching the blog's content-collection
   schema **directly to your GitHub repo** via the Contents API.
4. That push triggers Netlify's existing auto-deploy-on-push. The new post
   appears through the normal build — there's no separate "auto posts"
   system to maintain.

Required env vars (set in Netlify, never committed — see `.env.example`):
`GITHUB_TOKEN` (fine-grained PAT, Contents: Read & Write, scoped to this
repo only), `GITHUB_REPO`, `GITHUB_BRANCH`.

The function does **not** call an LLM to write prose — it assembles a
templated digest from curated headlines. Slotting in an AI-drafted
long-form version on top of that digest is a reasonable next step, but
should stay a reviewed editorial step rather than something that
auto-publishes unsupervised to a compliance-focused engineering blog.

## Design system

- **Canvas:** `#0B0F17` (midnight), card surfaces at `#10151C` / `#151B26`.
- **Type:** Plus Jakarta Sans (display/body), JetBrains Mono (data, code,
  live readouts, tab labels) — the monospace pairing is deliberate, not
  decorative: it's the same visual language Stripe/Vercel/Linear use for
  anything measuring or reporting a live system, which is exactly what the
  Live Systems Strip does.
- **Signal palette:** blue = engineering/primary, emerald = operational/
  secure, amber = advisory. Every accent color on the site maps to one of
  these meanings — nothing is colored purely for decoration.
- **Signature element:** `LiveSystemsStrip.astro` — a terminal-style status
  readout that renders the site's own "systems" (time, weather, security
  posture) rather than illustrating them. It's the one place the site takes
  a visual risk; everything else is deliberately restrained around it.

## Semantic web layer (this build)

Structured data is now colocated with the content it describes rather than
hand-rolled once in `<head>`:

| Schema type | Lives in | Describes |
|---|---|---|
| `ProfessionalService` + `WebSite` (`@graph`) | `Layout.astro` | Present on every page |
| `Service` × 4 | `BentoGrid.astro` | Same source array driving the visible cards |
| `FAQPage` | `FAQSection.astro` | Same `faqs` array driving the accordion — eligible for Google's FAQ rich result |
| `Person` × 2 | `AboutTeam.astro` | Same `team` array driving the cards |
| `BlogPosting` + `BreadcrumbList` | `blog/[slug].astro` | Built from each post's own frontmatter |
| `Blog` + `BreadcrumbList` | `blog/index.astro` | Listing page, `blogPost` references every published post |

Plus: `<link rel="alternate" type="application/rss+xml">` for feed
autodiscovery, `<html lang="en-KE">`, and a real XML sitemap
(`@astrojs/sitemap`, already wired in `astro.config.mjs`).

**Why this didn't reintroduce the CSP hash problem:** it would have, by
hand. Real structured data legitimately varies per page — a blog post's
`BlogPosting` block is never the same JSON twice, and that's the whole point
of it existing. Manually pinning a hash per unique block stops being
tractable the moment the daily auto-publish pipeline starts adding posts
unattended. `scripts/lib/collect-inline-script-hashes.mjs` solves this once: it's
the shared core both `scripts/generate-headers-vercel.mjs` and
`scripts/generate-headers-netlify.mjs` call as part of `npm run build` /
`npm run build:netlify`. It scans every built HTML file for every inline
`application/ld+json` block, computes each one's exact SHA-256, and writes
the complete headers config — CSP included — from scratch on every build.
Neither `netlify.toml` nor `vercel.json`'s `headers` array is hand-maintained
anymore; it's generated, correct by construction, on every build.

I verified this end-to-end, not just by reading the code: ran a real
`npm install && npm run build` in the sandbox before calling this final.
5 pages built, 12 inline structured-data blocks found across them,
correctly deduplicated to 8 unique hashes (matches hand-count: 1 shared
Organization/WebSite graph + 4 homepage-only component schemas + 3 distinct
per-post `BlogPosting` graphs). `dist/_headers` and `dist/sitemap-index.xml`
both generated correctly.

**One real bug found and fixed in the process:** `@astrojs/sitemap`'s
latest release (3.7.3 at time of writing) crashes on `astro:build:done`
against Astro 4.16 with `Cannot read properties of undefined (reading
'reduce')` — an upstream version-compatibility break, not anything in this
codebase. `package.json` pins `@astrojs/sitemap` to the exact known-working
`3.2.1` (no caret) rather than a range, specifically to stop a routine
`npm install` from silently reintroducing that failure. `package-lock.json`
is included in this delivery for the same reason — `npm ci` reproduces the
exact dependency graph that was actually built and verified, not just one
that resolves.

## Chat widget & site speed (this build)

### Chat widget

`ChatWidget.astro` + `api/chat.js` (Vercel) / `netlify/functions/chat.js`
(Netlify) — a floating chat button, present on every page via `Layout.astro`,
backed by Claude via the Anthropic API.

- **The browser never holds an API key.** It only ever talks to
  `/api/chat`, same-origin — which is why `connect-src 'self'` in the CSP
  didn't need to change at all to add this feature. That's not an
  accident; it's the payoff of every other feature on this site already
  being built as "client → our own `/api/*` proxy → the real third party,"
  never "client → third party directly."
- **Grounded, not open-ended.** The system prompt in `api/chat.js` only
  contains facts already published elsewhere on the site (services,
  compliance frameworks, team, contact info) and explicitly forbids the
  four things that would actually be dangerous coming from a chatbot on a
  cybersecurity firm's own site: quoting pricing, claiming anything about a
  *visitor's own* security posture, inventing case-study details, and
  following instructions embedded in a user message that try to override
  its own rules.
- **Streams the response** — Anthropic's server-sent-event stream is piped
  straight through the proxy to the browser, which renders it token-by-
  token. I tested the client-side buffering logic against a stream
  deliberately split at awkward byte offsets (mid-event, mid-JSON-line) —
  the realistic failure mode for a naive implementation — and it
  reassembles correctly.
- **Honest about its own rate limiting.** The in-memory counter in
  `api/chat.js` only protects a single warm Edge instance for its own
  lifetime — it is NOT real distributed rate limiting across Vercel's edge
  network, and resets on every cold start. It's a real first line of
  defense against one runaway client, not a production-grade solution. If
  this becomes a real cost concern, put Upstash Redis or Vercel KV in front
  of it instead of trusting this counter alone.
- Requires `ANTHROPIC_API_KEY` (console.anthropic.com). Without it, the
  widget still opens and responds — with a plain "not configured yet"
  message, not a silent failure or a fake success.

### A real bug this caught, worth understanding

Adding the chat widget's tiny inline bootstrap script (and a matching one
for lazy-loading the Tech Intel Hub, and one injected automatically by
`@vercel/speed-insights/astro`) broke the CSP hash generator — silently.
The generator only ever scanned `<script type="application/ld+json">`
blocks, because that was the only kind of inline script on the site when it
was written. None of these three new scripts have that `type`, so the old
scanner would have produced a CSP that **build successfully, deploy
successfully, and then silently block all three scripts in every visitor's
browser** — the chat button would render but do nothing on click, same for
the Tech Intel Hub's lazy-load and Speed Insights' own tracking.

This is exactly why `npm run build` exiting 0 was never treated as
"verified" anywhere in this project. `scripts/lib/collect-inline-script-
hashes.mjs` (renamed from `collect-json-ld-hashes.mjs`, since it's no
longer JSON-LD-specific) now matches ANY inline `<script>` with no `src`
attribute, regardless of `type` — verified against every literal
script-tag shape actually present in this project's build output, and then
proven by writing a small script that re-parses the built HTML, extracts
every inline script, hashes it, and confirms each one is actually present
in the generated CSP. Zero would be silently blocked, checked directly
rather than assumed.

### Site speed

- **Nothing new on the critical path.** The chat widget's button is plain
  static HTML/CSS — visible at zero JS cost. The script that actually
  knows how to open the panel and call the API loads only on first click or
  focus, never during initial page load.
- **Tech Intel Hub is now lazy-loaded** the same way, via
  `IntersectionObserver` — it sits well below the fold, so there's no
  reason to spend any of the initial JS budget loading it before a visitor
  scrolls near it.
- **`@vercel/speed-insights`** is wired into `Layout.astro` so Core Web
  Vitals get measured in production going forward, instead of just
  asserting the site is fast. It's a no-op outside Vercel and in dev mode.
- **Considered and deliberately skipped:** inlining critical CSS (would
  improve first paint, but conflicts with keeping `inlineStylesheets:
  "never"` for CSP purity — a real tradeoff, not solved here) and an
  explicit `Cache-Control` header for HTML documents (Vercel's per-
  deployment static serving already invalidates cleanly on every deploy;
  a hand-rolled path-exclusion pattern to add one felt like unverifiable
  risk for uncertain gain without live A/B testing against the platform).

### Accessibility: a real WCAG audit, not an assumption

Computed actual contrast ratios (relative luminance per the WCAG formula,
not a visual guess) for every text/background combination used anywhere on
the site. Found two real AA failures:

- `ink-muted` (#64748B) and `ink-faint` (#3D4759) — both used extensively
  at 10–13px across the footer, blog metadata, tab labels, and the Live
  Systems Strip labels. Neither is large/bold enough to qualify for the
  "large text" 3:1 exemption, so both needed the full 4.5:1 AA-normal
  threshold. They measured 4.03:1 and 2.05:1 — genuine failures, not edge
  cases. Replaced with `#7E8CA0` (5.61:1) and `#748094` (4.80:1),
  verified against BOTH backgrounds actually used (`#0B0F17` page canvas
  and `#10151C` card surface), with the darker value correctly kept as the
  less-prominent of the two. Because these are Tailwind theme tokens, the
  fix is two hex values in `tailwind.config.mjs` — every one of the ~30
  existing usages across the codebase is corrected automatically, nothing
  else needed to change.
- White text on `signal-blue` as a solid button/link background (the chat
  widget's Send button, the skip-to-content link) measured 3.68:1 against
  the 4.5:1 requirement. Fixed by using the already-existing
  `signal-blue-dim` token (6.7:1) for those two specific usages instead of
  introducing a new color.

### Two real bugs in the CSP generator, found by actually tracing a result instead of trusting a pass

Adding the chat widget, the lazy-load bootstraps, and Speed Insights each
surfaced a genuine bug in `scripts/lib/collect-inline-script-hashes.mjs` —
worth understanding both, because the second one specifically defeated the
verification method used to catch the first one.

1. **Type-specific matching.** The original scanner only matched
   `<script type="application/ld+json">`. The moment other inline scripts
   existed with no `type` at all, they went unhashed — a build that
   succeeds and deploys fine, then silently blocks those scripts in every
   visitor's browser. Fixed by matching any src-less `<script>` regardless
   of type.
2. **Regex doesn't understand HTML comments.** `Layout.astro` contains a
   documentation comment that describes the JSON-LD pattern using the
   literal text `` `<script type="application/ld+json">` `` for human
   readers. The fixed regex from (1) matched that literal text *inside the
   comment* as if it were a real opening tag, then consumed everything up
   to the *next real* `</script>` as its "content" — silently swallowing
   the actual Organization/WebSite JSON-LD script (present on **every
   single page**) into a corrupted match and hashing the wrong content
   entirely. That script would have been blocked by CSP sitewide. The
   verification script written to catch exactly this kind of problem
   didn't catch it, because it reused the same regex to check itself —
   comparing a buggy result against itself always agrees.

   Rather than patch the regex a third time, `collect-inline-script-
   hashes.mjs` now uses **parse5** (the same HTML5 parser jsdom uses) to
   walk a real parsed DOM tree instead of pattern-matching raw text. A
   parser tokenizes comments and tags correctly by construction — this
   class of bug isn't patched, it's structurally impossible now. `parse5`
   is a real `dependency`, not a `devDependency` — it runs during the
   production build itself.

   The fix was confirmed with a **second, genuinely independent** parser
   (`cheerio`, built on `htmlparser2` — a different codebase than
   `parse5`) re-checking the generator's output from scratch, plus a
   manual trace confirming the Organization/WebSite script's hash now
   corresponds to its real JSON content, not comment text. Both platform
   builds (`npm run build` and `npm run build:netlify`) were re-verified
   after the fix.
